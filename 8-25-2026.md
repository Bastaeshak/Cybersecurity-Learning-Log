Alert — Potentially Unwanted Application Remediated

05:31:02 UTC — PUA:Win32/BundleLoader detected.

05:31:04 UTC — Quarantine succeeded on the first attempt.

07:31:04 UTC — Follow-up rescan returned CLEAN with no reappearance.

Verdict

Verdict: True Positive — Successfully Remediated
Severity: Low
Action: Resolved
Escalation: Not required
Tuning: No tuning recommended

The PUA was genuinely present, making the detection a true positive. However, endpoint protection successfully contained it, and the clean rescan provided evidence that it did not persist.

I also documented that the dataset did not provide the actual executable or its hash. If those artifacts were available, I would perform additional reputation analysis using approved threat-intelligence tooling and, if permitted, analyze the file in an isolated sandbox.

Key Lesson

This alert reinforced the importance of separating detection from remediation. A true-positive detection does not necessarily mean an active threat remains on the endpoint.

Alert — First-Time Sign-In Properties: Guest Account
Investigation

Investigated unusual authentication activity involving Bexley consultant Eleanor Walsh and guest account:

ewalsh.ext@cloudora.io

The original alert involved a successful 21:47 UTC sign-in from 198.51.100.77 using macOS/Safari without an MFA challenge.

The shift handover confirmed that:

Eleanor is an authorized Bexley Payroll Integrations consultant.

Bexley is currently undergoing go-live work.

The Bexley guest-access policy predates the current MFA baseline and therefore does not currently require MFA.

Historical sign-in activity also showed that the triggering login matched Eleanor's established IP, location, OS, and browser.

However, deeper review identified a separate login from:

192.0.2.146

Device: Windows
Browser: Chrome
Network: Unknown/hosting infrastructure

This did not match Eleanor's established sign-in pattern.

I searched 192.0.2.146 across the available sign-in records and found no other authentication activity associated with that IP, meaning I could not establish it as a previously known source.

Additional Correlation

I expanded the investigation into the proxy/egress evidence.

On Oct. 7 at 11:02 UTC, an ewalsh.ext session accessed 34 documents in the Payroll-Mapping SharePoint library over approximately 25 minutes.

On Oct. 8 at 23:52 UTC, another ewalsh.ext session performed OAuth consent for “Bexley Sync Utility.”

The proxy logs do not provide the originating IP for those sessions, so I could not conclusively correlate the activity with 192.0.2.146.

Verdict

Verdict: Insufficient Data
Severity: Medium
Action: On Hold / Additional investigation required
Monitoring: Continue monitoring account activity
Escalation: Not yet escalated

Additional evidence requested includes:

Confirmation from Eleanor/Bexley regarding the 192.0.2.146 session, session-level authentication information, SharePoint activity associated with the session, and correlation between the anomalous authentication and subsequent account activity.

I also documented that the account should continue to be monitored for new IP addresses, unfamiliar devices/browsers, unusual SharePoint activity, OAuth consent activity, and further activity involving 192.0.2.146.

The escalation criteria were also documented. The case should be escalated to the vCISO if Eleanor denies the session, unauthorized client/payroll data access is confirmed, malicious activity expands beyond the currently observed scope, or the activity cannot be bounded with available evidence.

Key Lesson

This investigation showed why analysts should keep pivoting through available evidence even when the original alert appears explainable.

The original 21:47 sign-in had strong benign indicators. Additional log review, however, revealed activity that prevented me from confidently closing the investigation.

Instead of forcing a True Positive or False Positive verdict without enough evidence, I documented the gaps and selected Insufficient Data.

Alert — TCP Port Sweep
Investigation

Investigated a TCP port-sweep alert originating from:

203.0.113.44 — LDN-SCAN-01

The host probed 3,800+ TCP ports across 160 internal hosts using sequential SYN probes with no data transfer.

The scanner's standing schedule is:

Monday 22:00 → Tuesday 03:00 UTC

The detected activity occurred:

Sunday 23:30 → Monday ~01:1x UTC

At first glance, the timing appeared suspicious because it occurred outside the normal scanning schedule.

However, reviewing the shift handover identified CHG-2101, which temporarily moved that week's vulnerability scan to:

Sunday 23:00 → Monday 03:00 UTC

The source IP, scanner hostname, traffic pattern, and timestamps therefore matched the documented authorized activity.

Verdict

Verdict: False Positive — Authorized Vulnerability Scan
Severity: Informational
Action: Resolved
Escalation: Not required
ServiceNow Resolution Code: Resolved by Change

Tuning Recommendation

Recommended change-window-aware tuning.

TCP port-sweep alerts could be suppressed or reduced in severity when both of the following conditions are satisfied:

The source matches the authorized LDN-SCAN-01 / 203.0.113.44 vulnerability scanner.

The activity occurs within an active approved vulnerability-scanning/change window.

Scanning outside the approved window or originating from an unexpected source should continue generating alerts normally.

Key Lesson

This alert demonstrated why SOC analysts need to correlate detections with change-management information.

The detection itself was technically correct—the host really was scanning thousands of ports. The context established that the activity was authorized, turning what initially looked like reconnaissance into a False Positive.
